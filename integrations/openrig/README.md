# Native development workspace

This integration uses **stock OpenRig 0.6.10** from npm (`@openrig/cli`, pinned in
`runtime/SOURCE`), with Node **24.14.0** for the machine's platform (linux-arm64 on dev-server).
The owner's fork and its local patches are retired (2026-10-14): upstream now covers them or
the platform does without. Models and login remain the harness's choice. The existing loop
remains execution authority.

A seat's account reaches it through the seat launcher (seat-bin and agent-run), which hands the
seat that account's own login; `dev-workspace --account ID` names it for one seat. No spec field
carries it: stock OpenRig refuses `config_home`, and the platform no longer writes it.

## Upstream workflow and current integration boundary

The [official getting-started guide](https://www.openrig.dev/docs/getting-started)
demonstrates mixed harness rigs: Conveyor has two Claude and two Codex seats;
Product Team has four Claude and three Codex seats. **OpenRig supports both native
Claude Code and Codex seats.** This platform deliberately starts one owner-directed
control seat at a time over the existing loop, not another agent dispatcher.

Native tmux discovery/adoption applies to compatible terminal sessions, not arbitrary
Claude Desktop conversations. A catalog link, process inventory, message delivery, or
successful MCP read does not mean OpenRig owns or can steer a Desktop session. Keep
session ownership explicit and do not launch replacements for existing controllers.

Account profiles are a separate capability from harness support, and there are two
distinct mechanisms; do not conflate them. OpenRig's own built-in provider-account
registry, unrelated to this platform's account service, still accepts Codex
profiles only, with account-switch execution unwired and reporting `failed_safely`
with `switch_execution_not_yet_wired`; that registry was empty at inspection on
2026-09-24 and remains unconfigured. That is **not** a restriction on Claude seats,
and it is **not** the mechanism this platform uses.

`dev-workspace --account` asks the platform's one resolver (the choice `ai-account resolve`
makes; see the section AC of `docs/spec/SDD.md`). Once the named account is verified and eligible, the seat
launcher starts the seat on that account.

All control contexts may name their own sessions under the shared
[session-naming contract](../../docs/session-naming.md). Native conversation titles,
OpenRig seat labels, project names, and account identities are different metadata.

## Repeatable installation

On dev-server, `bootstrap.sh` (step "rigs") installs it and nothing else does: Node 24.14.0 under
`/opt/dev-platform/openrig-runtime/` (checked against a pinned SHA-256), and `@openrig/cli` at the
version in `runtime/SOURCE`, installed from npm as `nobody` into `openrig-runtime/app`. To
upgrade, change the version there, validate the agent specs and rig shapes against it
(`rig agent validate`, `rig spec validate`), and run bootstrap. The expected executables are:

```text
openrig-runtime/app/node_modules/.bin/rig
openrig-runtime/node-v24.14.0-linux-arm64/bin/node
```

Activate a checked platform release under `/opt/dev-platform/current`
and link its `bin/dev-workspace`, `bin/ai-work`, and `bin/rig` into `~/.local/bin` without
replacing unrelated files. Publish the shared
`development-workspace` skill through Skill Workshop; this directory deliberately
does not fork its body. Install Claude/Codex and authenticate through their native
flows. Never copy authentication material into RigSpecs or project files.

Set OpenRig's native workspace configuration to the catalog generated by
`ai-work`, outside product repositories. On this host that root is
`~/.local/state/dev-platform/workspace`. Configure `workspace.root`,
`workspace.catalog_path` (`workspace.yaml` under that root),
`workspace.projects_root`, and `workspace.slices_root` consistently with that
catalog, and allowlist the workspace through OpenRig's native file configuration.
Do not overwrite another catalog or import historic sessions as active seats.
The owner's activation uses native `rig config set <key> <value>` with this exact
configuration contract (expand the root to an absolute path):

| Key | Value |
| --- | --- |
| `daemon.host` | `127.0.0.1` |
| `snapshots.periodic.enabled` | `false` |
| `retention.enabled` | `false` |
| `recovery.auto_drive_provider_prompts` | `false` |
| `policies.claude_compaction.enabled` | `false` |
| `policies.idle_gate_qitem.auto_register` | `off` |
| `workflow.exception_routing` | `human_only` |
| `ui.timezone` | `Etc/UTC` |
| `workspace.root` | `~/.local/state/dev-platform/workspace` |
| `workspace.catalog_path` | `<root>/workspace.yaml` |
| `workspace.projects_root` | `<root>/projects` |
| `workspace.slices_root` | `<root>/missions` |
| `files.allowlist` | `["workspace:<root>"]` |
| `progress.scan_roots` | `["workspace:<root>"]` |

Preserve any unrelated approved file roots when applying the two list settings;
never broaden them to the whole home directory. Inspect existing configuration
first and do not run blanket `rig setup` as an upgrade. These settings select a
manual, local-only control surface; they do not enable system schedules. An existing
daemon must have been started with the user's native harness configuration.

## Owner-facing entry

`dev-workspace` opens the stock OpenRig TUI. If the daemon is conclusively stopped,
it uses `rig daemon start --no-kernel`. It does not restore rigs or start agents.
An unhealthy, stale, or ambiguous daemon is reported, not restarted. Optional
`dev-workspace open --shared` only attaches an already configured kernel terminal;
it never creates a kernel. The default does not depend on a kernel.

Starting an agent is a separate explicit action:

```sh
dev-workspace plan codex --cwd /absolute/path/to/a/worktree
dev-workspace start codex --cwd /absolute/path/to/a/worktree
# Alternative harness:
dev-workspace start claude --cwd /absolute/path/to/a/worktree
# Pin a specific native account for this seat:
dev-workspace start codex --cwd /absolute/path/to/a/worktree --account openai
```

The launcher previews with native `rig up --plan` before launch. It preserves
upstream permission prompts rather than passing `--yes`. The `start` verb starts
only the named control seat; worker dispatch still requires the owner's request.
Without `--account`, an existing `development-codex` or `development-claude` rig
is reused with `--existing`, never cloned. With `--account`, the rig name is
`development-<runtime>-<account>` (e.g. `development-codex-openai`), so two
accounts on the same runtime never collide on one rig; that name is looked up and
reused the same way. Reuse preserves the persisted session's original working
directory; `--cwd` applies to a new rig only. For another task, use the shared
task/worktree workflow rather than silently repurposing a live session. Archived
or duplicate rigs require explicit resolution.

`--account` first checks the folder's configuration files for an override of
authentication or the provider, then resolves the named account with the one resolver
(see the section AC of `docs/spec/SDD.md`). It refuses immediately, in the resolver's own words, if the
account cannot serve the seat — before touching rig inventory or writing anything; a
named account is never substituted. Otherwise it renders that per-account
RigSpec (OpenRig's runtime name and the folder) into
`~/.local/state/dev-platform/openrig/<rig-name>.yaml` (a state directory, not a
product repository; never committed) and passes that generated spec to `rig up`
in place of the shared `codex.yaml`/`claude.yaml`. Reusing an existing per-account
rig still re-resolves the account plan first, as identity revalidation, not
reselection.

`dev-workspace start engineer --cwd <team folder>` starts the control rig from
`engineer.yaml`: a control seat, a Codex overseer and an empty `workers` pod. Worker seats
join and leave it one loop worktree at a time with `add-worker` and `remove-worker`;
see `docs/rig-working-branches.md`.

The launcher removes inherited `CODEX_HOME` and `CODEX_THREAD_ID` from its child
environment so standalone Codex uses its native personal store. It does not
rewrite either store or migrate preserved OpenClaw conversations. An already running
daemon retains its own environment; changing a caller cannot repair that daemon.

## Native tool access from coding sessions

A sandboxed coding shell may not reach the loopback daemon over HTTP. Keep the
shell sandbox intact; do not enable blanket network access to fix that symptom.
OpenRig provides its own stdio MCP server, which the harness can launch through
its supported MCP configuration. Inspect existing MCP registrations first; keep
an existing correct `openrig` registration instead of creating a duplicate.
Register in the personal harness configuration, not a product repository:

```sh
codex mcp add openrig -- "$HOME/.local/bin/rig" mcp serve
claude mcp add --scope user --transport stdio openrig -- "$HOME/.local/bin/rig" mcp serve
```

Run those commands from the normal personal login environment (without an
inherited managed `CODEX_HOME`). Reopen the coding session after registration
and use the native `rig_ps` tool to confirm daemon access. Successful registration
alone is not proof of connectivity. A successful read proves discovery and
transport only, not message acknowledgement, worker steering, loop execution,
or authorization for any subsequent action. The tool server does not replace
the existing loop's dispatch authority.

## Boundaries and verification

The specs import no upstream agent teams, select no hooks or runtime configuration
fragments, and force no model. OpenRig still has its own built-in context and
native harness projection behavior; an explicit seat start may project guidance
and supported integration files into the selected worktree. Use an isolated
worktree, and inspect the native plan first.

`tests/test_openrig_launcher.py` exercises real launcher process boundaries with a
harmless CLI fixture: opening never boots a kernel/seat, an existing rig is reused,
failed previews block execution, and ambiguous status fails closed. Validate the
RigSpecs with the installed native `rig up ... --plan` as a separate integration
check. Offline launcher tests do not establish live steering, authentication, or
end-to-end loop correctness. No automatic installation or daemon upgrade occurs.

`tests/test_openrig_profile.py` covers the `--account` path the same way, with a fake account
state for the real resolver, and checks that no generated spec carries `config_home`.

Both native plans passed on 2026-09-24 with the pinned CLI, with the expected
`permission_policy absent; launch_posture=floor` warning. No agent was started by
that check. The pinned parser requires `uses.plugins`, not the obsolete
`uses.hooks` key still shown in some upstream AgentSpec documentation.

Upstream contracts: [RigSpec](https://github.com/mvschwarz/openrig/blob/main/docs/reference/rig-spec.md),
[AgentSpec](https://github.com/mvschwarz/openrig/blob/main/docs/reference/agent-spec.md),
[project workspace](https://github.com/mvschwarz/openrig/blob/main/docs/reference/project-workspace.md).
Revalidate against the installed CLI before changing the pinned version.

### Seat refresh by seat type

Each seat type's agent spec sets OpenRig's own lifecycle (`defaults.lifecycle`), so a seat's
session is renewed the way its job needs, with no code of ours:

| Seat | `compaction_strategy` | `restore_policy` | Why |
| --- | --- | --- | --- |
| control (lead) | `handover` | `resume_if_possible` | It holds the plan: when its context fills, a fresh successor starts from its recap. |
| overseer (reviewer) | `default-compaction` | `relaunch_fresh` | A review needs the diff, spec and check, not history. |
| worker | `default-compaction` | `relaunch_fresh` | One task, one worktree, one session. |

The platform's 20/30-turn rule does not apply to seats: they follow this lifecycle instead.

### Permissions in personal checkouts

A new `dev-workspace start claude|codex` seat, and an `add-worker` seat, in a personal checkout
(tier 1 or 2 in `~/.config/dev-platform/repos.conf`) carries `permission_policy: "builtin:yolo"`: Claude launches with
`--dangerously-skip-permissions` and Codex with `-s danger-full-access -a never`, for that seat only.
The launcher prints a notice when it does this. A folder that is not a Git checkout, a professional
checkout, an already running rig (which keeps its launch posture), and the engineer control rooms and
engagement specs are unchanged. The daemon-wide `OPENRIG_YOLO` switch is not used. The guard hook
still governs pushes, merges and restarts; it is the only barrier left on these seats.

## Provenance and compatibility

Pinned: stock `@openrig/cli` 0.6.10 (`3001cc43`). The platform launcher refuses another version
until the integration is rechecked. Checked on 2026-10-14 against 0.6.10 on a scratch daemon:
`rig agent validate` accepted the control, overseer and worker specs with their lifecycle
defaults, and `rig spec validate` accepted `claude.yaml`, `codex.yaml`, `engineer.yaml` and the
build, review and solo shapes; it refuses a `config_home` member field, which the platform no
longer writes. Keep the pinned Node directory first on `PATH`; native bindings are not validated
under arbitrary host Node versions.
